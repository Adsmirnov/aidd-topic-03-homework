# Анализ приложения

## 1. Назначение и технологический стек

Investing Demo — веб-приложение для просмотра каталога акций, их текущих котировок и графика исторических цен. Пользователь может зарегистрироваться и войти; вошедшим пользователям доступны операции управления акциями через веб-интерфейс. Те же записи доступны через REST API.

Стек исходной версии:

- Python и Django 4.1.7 — серверное веб-приложение, маршрутизация, шаблоны, формы, ORM и встроенная аутентификация.
- Django REST Framework (DRF) и django-filter — REST API, сериализация, фильтрация и пагинация.
- PostgreSQL — основная база данных; конфигурация драйвера задана через `psycopg2-binary`.
- Celery и Redis — фоновое периодическое получение котировок.
- Tinkoff Invest API (`tinkoff-investments`) — первоначальный каталог инструментов, текущие цены и свечи.
- Plotly — график цен на странице акции; Bootstrap — стили веб-интерфейса.

Инфраструктура PostgreSQL и Redis описана в `docker-compose.yml`. Параметры подключения Django находятся в `config/settings.py`; в исходном состоянии там же задана пустая строка `TINKOFF_TOKEN`.

## 2. Структура проекта

- `manage.py` — точка входа в команды Django.
- `config/` — настройки проекта, корневые URL, WSGI/ASGI и интеграция Celery (`settings.py`, `urls.py`, `wsgi.py`, `asgi.py`, `celery.py`).
- `dashboard/` — каталог акций и основной пользовательский интерфейс:
  - `models.py`, `forms.py`, `views.py`, `urls.py`, `admin.py` — модель `Share`, форма и HTML-представления, маршруты и настройка админки;
  - `api/` — маршруты, DRF ViewSet, фильтр и сериализатор REST API;
  - `services/market_data.py` — запрос текущей котировки у Tinkoff Invest API;
  - `services/graph.py` — получение свечей и генерация графика Plotly;
  - `tasks.py` — фоновое обновление текущих котировок;
  - `management/commands/add_shares.py` — команда загрузки инструментов из API;
  - `migrations/` — семь последовательных миграций модели акций;
  - `templates/dashboard/` — список, карточка, формы создания/редактирования и подтверждение удаления;
  - `static/dashboard/` — Bootstrap CSS и стили макета.
- `user/` — формы и представления регистрации, входа и выхода, их URL, шаблоны и CSS. `user/models.py` не объявляет собственную модель, а получает стандартную модель пользователя Django через `get_user_model()`; отдельные миграции приложения отсутствуют.
- `requirements.txt` — закреплённые версии Python-зависимостей.
- `README.md` — краткие команды запуска PostgreSQL, загрузки акций, Celery и описание API.
- `HOMEWORK.md` — условие учебной работы.

## 3. Архитектура и взаимодействие компонентов

### Веб-интерфейс и аутентификация

Корневой маршрутизатор в `config/urls.py` подключает Django Admin по `admin/`, интерфейс `dashboard` в корне и маршруты `user`. `dashboard/urls.py` связывает URL со списком акций, карточкой акции и представлениями создания, редактирования и удаления. Список и карточка доступны без входа; CRUD-представления защищены `IsUserAuthenticatedMixin`.

Регистрация и вход реализованы в `user/views.py` через формы из `user/forms.py` и стандартные механизмы Django `authenticate`, `login` и `logout`. Для хранения состояния аутентификации включены middleware сессий и аутентификации. В `config/urls.py` префикс приложения `user` задан как `user` без завершающего `/`; итоговые адреса образуются прямой конкатенацией этого префикса с маршрутами `user/urls.py`.

### REST API

Маршруты подключаются как `dashboard/api/` → `dashboard/api/urls.py` → `v1/` → `dashboard/api/v1/urls.py`. `DefaultRouter` в `dashboard/api/v1/router.py` регистрирует `ShareViewSet` по ресурсу `shares`, доступному по `/api/v1/shares/`. `ModelViewSet` предоставляет операции списка, получения записи, создания, изменения и удаления. `ShareSerializer` задаёт поля представления; `ShareFilter` фильтрует по `name` и `ticker`, `OrderingFilter` сортирует по этим полям. Настройки DRF в `config/settings.py` включают пагинацию `LimitOffsetPagination` с размером страницы 100 и backend django-filter. Для ViewSet не заданы отдельные классы разрешений.

### Котировки и фоновые задачи

`dashboard/management/commands/add_shares.py` открывает клиент Tinkoff, получает перечень акций и сохраняет инструменты через `Share.objects.get_or_create()`.

Celery-приложение создаётся в `config/celery.py`, читает настройки Django с префиксом `CELERY_` и автоматически обнаруживает задачи. Broker задан как Redis `redis://127.0.0.1:6379/0`. В расписании Celery Beat задача `dashboard.tasks.update_last_price` настроена на запуск с интервалом `10.0` секунд. Она проходит по записям `Share`, вызывает `dashboard.services.market_data.get_last_data()`, сохраняет новую цену и вычисленный признак направления изменения. Ошибки отдельных запросов записываются через logger `main` из `config/settings.py`.

`get_last_data()` запрашивает у Tinkoff последнюю цену для FIGI акции. `dashboard/services/graph.py` при открытии карточки получает через тот же API дневные свечи за последние 180 дней и формирует встраиваемый HTML-график Plotly. Этот график формируется из ответа внешнего API; отдельной модели или таблицы для хранения истории цен в приложении нет.

### Хранение данных и запросы к базе

Django ORM работает с PostgreSQL, указанным в `DATABASES` в `config/settings.py`; `docker-compose.yml` описывает контейнер PostgreSQL с базой `investing` и Redis. Веб-представления читают и изменяют данные через ORM. DRF ViewSet использует queryset `Share.objects.all()`, а Celery-задача обновляет котировки отдельными запросами к ORM. Отдельного слоя репозиториев или сервисного слоя доступа к БД нет.

## 4. Библиотеки и внешние зависимости

Прямо используемые библиотечные компоненты и зависимости, закреплённые в `requirements.txt`:

- `Django==4.1.7` — веб-фреймворк и ORM.
- `djangorestframework==3.14.0`, `django-filter==22.1` — REST API, фильтрация.
- `celery==5.2.7`, `redis==4.5.1` — фоновые задачи и клиент брокера Redis.
- `psycopg2-binary==2.9.5` — PostgreSQL-драйвер.
- `tinkoff-investments==0.2.0b50` — клиент Tinkoff Invest API; `tinkoff==0.1.1` также указан отдельно в зависимостях.
- `plotly==5.13.1` — построение графика.
- `django-crispy-forms==2.0`, `crispy-bootstrap3==2022.1` — оформление Django-форм.
- `black`, `isort` — инструменты форматирования и сортировки импортов.
- Остальные закреплённые пакеты в файле являются транзитивными зависимостями используемых библиотек.

В шаблонах используются локальные CSS-файлы Bootstrap и внешние ресурсы CDN: Plotly, jQuery, Popper, Font Awesome, Moment.js и Tempus Dominus. Frontend-сборка и отдельный JavaScript-пакетный менеджер в проекте не настроены.

## 5. Модель данных и история миграций

Предметная модель приложения — `dashboard.models.Share` (таблица Django по умолчанию `dashboard_share`). Связей с другими предметными моделями нет.

| Поле | Тип и ограничения | Назначение |
|---|---|---|
| `id` | `BigAutoField`, первичный ключ | Идентификатор записи |
| `figi` | `CharField(max_length=255)`, уникальное | Идентификатор инструмента Tinkoff |
| `isin` | `CharField(max_length=255)` | Международный идентификатор ценной бумаги |
| `name` | `CharField(max_length=255)` | Наименование компании |
| `ticker` | `CharField(max_length=10)`, уникальное | Биржевой тикер |
| `currency` | `CharField(max_length=20)` | Валюта котировки |
| `uid` | `CharField(max_length=255)`, уникальное | UID инструмента Tinkoff |
| `last_price` | nullable/blank `FloatField` | Последняя загруженная цена |
| `is_trend_high` | nullable/blank `BooleanField` | Признак направления изменения цены |
| `updated_at` | `DateTimeField(auto_now=True)`, допускает `null` | Время обновления записи |

Последовательность миграций в `dashboard/migrations/`:

1. `0001_add_share.py` создаёт `Share` с `id`, `figi`, `isin`, `name`, `ticker`, `currency`.
2. `0002_update_share.py` добавляет уникальность для `figi` и `ticker`.
3. `0003_add_uuid.py` добавляет уникальное поле `uid` (в миграции оно названо так, хотя поле модели называется `uid`, а не UUID-тип).
4. `0004_add_last_price.py` добавляет `is_trend_high` и `last_price`, а также задаёт отображаемые имена части полей.
5. `0005_add_verbose_name.py` уточняет отображаемое имя `name`.
6. `0006_add_verbose_name.py` задаёт отображаемое имя `ticker`.
7. `0007_add_updated_at.py` добавляет `updated_at`.

Пользовательские данные хранятся стандартными моделями `django.contrib.auth`; проект не задаёт `AUTH_USER_MODEL` и не содержит пользовательских миграций. Других моделей для уведомлений, портфелей, сделок, стратегий или сохранённой истории котировок исходный код и миграции не объявляют.

## 6. Обработка запросов и работа с БД

1. Django принимает HTTP-запрос и выбирает маршрут по `config/urls.py`, затем по URL-файлу приложения.
2. HTML-представления используют generic views Django и шаблоны. Список выполняет выборку `Share` с сортировкой по названию и пагинацией по 100 записей; создание и редактирование связывают `ShareModelForm` с ORM. Удаление выполняется через `DeleteView`. Для CRUD в веб-интерфейсе проверяется аутентификация.
3. Карточка загружает запись `Share` по первичному ключу, затем запрашивает свечи у Tinkoff и вставляет Plotly-разметку в шаблон `dashboard/templates/dashboard/detail.html`.
4. API-запрос обрабатывается DRF `ShareViewSet`: queryset читается через ORM, serializer преобразует данные между моделью и JSON, а фильтры и сортировка ограничивают выборку. Пагинация включена глобально в настройках DRF.
5. Регистрация и вход проходят через формы и встроенную систему пользователей/сессий Django. Регистрационная форма проверяет формат email, совпадение паролей и наличие существующей учётной записи; пароль передаётся стандартному `create_user()`.
6. Celery Beat инициирует фоновую задачу обновления; задача запрашивает внешний API и сохраняет цену через ORM. Команда `add_shares` отдельно загружает исходный список инструментов в базу.

Автоматизированные тесты в `dashboard/tests.py` проверяют HTML-страницу списка и базовые операции REST API с акциями: чтение, создание, изменение и удаление, включая некорректные запросы.
