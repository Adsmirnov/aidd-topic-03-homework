## 1. Назначение и технологический стек

**Назначение.** Веб-приложение для просмотра российских и иностранных акций, торгуемых через брокера Тинькофф (Т-Банк): список акций с текущей ценой и направлением её изменения, карточка акции с графиком цены закрытия за полгода, ручное ведение справочника акций (добавление, редактирование, удаление) для зарегистрированных пользователей и REST API для того же справочника. Цены подтягиваются из Tinkoff Invest API фоновой периодической задачей.

**Стек (по `requirements.txt` и `config/settings.py`):**

| Слой | Технология (исходная версия) |
|---|---|
| Язык | Python 3 (версия не зафиксирована; зависимости 2023 года → Python 3.8–3.11) |
| Веб-фреймворк | Django 4.1.7 (MVT, class-based views) |
| REST API | Django REST Framework 3.14, django-filter 22.1 |
| Формы / UI | django-crispy-forms 2.0 + crispy-bootstrap3, Bootstrap 5.1.3 (локальный CSS), Plotly 5.13 для графиков |
| Фоновые задачи | Celery 5.2.7 (worker + beat), брокер Redis 4.5 |
| БД | PostgreSQL (образ `postgres` без версии), драйвер psycopg2-binary 2.9.5 |
| Внешний API | Tinkoff Invest API (gRPC) через `tinkoff-investments==0.2.0b50` |
| Инфраструктура | `docker-compose.yml`: PostgreSQL и Redis |

## 3. Архитектура и взаимодействие компонентов

Классический Django-монолит из двух приложений + фоновый процесс Celery.

```
 Браузер ──HTML──► Django views (dashboard, user) ──ORM──► PostgreSQL
 Клиент API ─JSON─► DRF ShareViewSet ─────────────ORM──►      ▲
                         │                                    │
 Карточка акции ──► services.graph ──gRPC──► Tinkoff Invest API (свечи, синхронно в запросе)
                                                              │
 celery beat (каждые 10 c) ─Redis─► celery worker ─► tasks.update_last_price
                                        └─► services.market_data ─gRPC─► Tinkoff API (цена)
                                        └─► UPDATE dashboard_share ───────────────► PostgreSQL
 manage.py add_shares ──gRPC──► Tinkoff API (список всех акций) ──► INSERT в PostgreSQL
```

* **Синхронная часть** — Django обрабатывает HTTP-запросы: страницы рендерятся шаблонами, API — через DRF. Единственный внешний вызов в запросе пользователя — построение графика на странице акции (`dashboard/views.py:29-38` → `dashboard/services/graph.py:11-36`).
* **Асинхронная часть** — Celery beat по расписанию (`config/celery.py:13-18`) ставит задачу `dashboard.tasks.update_last_price` в Redis; worker выполняет её: для каждой акции отдельно запрашивает последнюю цену и обновляет `last_price` и `is_trend_high` (`dashboard/tasks.py:7-29`).
* **Первичное наполнение** — management-команда `add_shares` запрашивает все акции у Tinkoff API и создаёт записи (`dashboard/management/commands/add_shares.py:11-22`).
* Настройки Celery читаются из Django settings с префиксом `CELERY_` (`config/celery.py:9`), задачи находятся автоматически (`config/celery.py:11`), Celery подключается при старте Django через `config/__init__.py`.

## 5. Модель данных

Одна прикладная сущность + стандартная модель пользователя Django.

### `Share` — акция (`dashboard/models.py:4-21`, таблица `dashboard_share`)

| Поле | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | BigAutoField | PK | |
| `figi` | varchar(255) | **unique**, NOT NULL | идентификатор инструмента в Tinkoff API, по нему запрашиваются цены и свечи |
| `isin` | varchar(255) | NOT NULL | международный код ценной бумаги |
| `name` | varchar(255) | NOT NULL | «Наименование компании» |
| `ticker` | varchar(10) | **unique**, NOT NULL | «Тикер» |
| `currency` | varchar(20) | NOT NULL | «Валюта» (код в нижнем регистре, как отдаёт API: `rub`, `usd`) |
| `uid` | varchar(255) | **unique**, NOT NULL | uid инструмента в Tinkoff API |
| `last_price` | float | NULL | «Текущая цена» |
| `is_trend_high` | boolean | NULL | «Растет цена» — направление последнего изменения |
| `updated_at` | timestamptz | NULL, auto_now | время последнего сохранения через `save()` |

Связей нет: акции ни с чем не связаны, в том числе с пользователями (справочник общий).

**История миграций:** 0001 — создание (figi, isin, name, ticker, currency); 0002 — уникальность figi и ticker; 0003 — `uid` unique (дефолт `""` только на время миграции); 0004 — `last_price`, `is_trend_high` + verbose_name (с опечатками: у `name` — «Валюта», у `ticker` — «Ти»); 0005, 0006 — исправление этих verbose_name; 0007 — `updated_at`.

### `auth.User` — стандартный пользователь Django

Используется как есть (`user/models.py:1-3`). При регистрации email записывается и в `username`, и в `email` (`user/forms.py:51`). Ролей и прав, кроме «вошёл / не вошёл», приложение не использует.

## 6. Обработка запросов и работа с БД

| Маршрут | Обработчик | Доступ | Что делает |
|---|---|---|---|
| `GET /` | `ShareListView` (`dashboard/views.py:20-26`) | все | список акций, сортировка по `name`, 100 на страницу |
| `GET /<pk>` | `ShareDetailView` (`dashboard/views.py:29-38`) | все | карточка + график (вызов Tinkoff API) |
| `GET/POST /create` | `ShareCreateView` | вошедшие | форма со всеми полями модели |
| `GET/POST /update/<pk>` | `ShareUpdateView` | вошедшие | то же для изменения |
| `GET/POST /delete/<pk>` | `ShareDeleteView` | вошедшие | подтверждение и удаление |
| `/api/v1/shares/` | `ShareViewSet` (`dashboard/api/v1/views.py:16-22`) | **все, без авторизации** | CRUD, фильтр `?name=`/`?ticker=` (точное совпадение), `?search=` (regex по name), `?ordering=name|ticker`, пагинация limit/offset по 100 |
| `GET/POST /userlogin/` | `AuthView` (`user/views.py:8-33`) | все | вход по email+паролю |
| `GET/POST /userregistration/` | `RegistrationView` (`user/views.py:36-55`) | все | регистрация + автоматический вход |
| `GET /userlogout/` | `LogoutView` (`user/views.py:58-64`) | все | выход |
| `/admin/` | Django admin | staff | управление `Share` |

Адреса раздела `user` выглядят как `/userlogin/`, потому что в `config/urls.py:7` префикс указан без слэша (`path("user", ...)`).

Проверка доступа в HTML-части — собственный миксин `IsUserAuthenticatedMixin` (`dashboard/views.py:11-17`): не вошедшего пользователя перенаправляет на главную (не на страницу входа).

Работа с БД — только через Django ORM: generic-views (`ListView`, `CreateView`, …), DRF `ModelViewSet`, в Celery-задаче — `Share.objects.filter(id=...).update(...)` (`dashboard/tasks.py:24-26`), в команде загрузки — `get_or_create` по всем полям (`add_shares.py:15-22`). Транзакции явно не используются (autocommit Django).

# Восстановленные функциональные требования

## 7. Основные функциональные возможности

1. Справочник акций, хранящийся в БД.
2. Публичный просмотр списка и карточки акции с графиком.
3. Регистрация, вход и выход пользователей.
4. Ручное ведение справочника (создание, изменение, удаление) вошедшими пользователями.
5. REST API для справочника акций с фильтрацией, поиском, сортировкой и пагинацией.
6. Первичная загрузка всех акций из Tinkoff Invest API командой.
7. Периодическое автоматическое обновление текущей цены и направления её изменения.
8. Администрирование справочника через Django admin.

## 8. Сценарии взаимодействия

**С1. Гость смотрит рынок.** Открывает `/` → видит таблицу «Тикер / Название / ISIN / Текущая цена», ячейка цены зелёная, если цена растёт, и красная иначе → кликает тикер → видит название, цену с валютой, время обновления и график цен закрытия за 180 дней.

**С2. Регистрация.** Гость нажимает «Войти» → «Зарегистрироваться» → вводит email и пароль дважды → при успехе сразу оказывается залогинен и перенаправлен на `/`; при ошибке видит сообщение на той же странице.

**С3. Вход и выход.** Вводит email и пароль → при успехе попадает на `/`, в шапке «Привет, <email>» и кнопка «Выход»; при ошибке — «Неверный логин или пароль! Повторите попытку.». «Выход» разлогинивает и возвращает на `/`.

**С4. Ведение справочника.** Вошедший пользователь видит кнопку «Добавить» и колонку «Управление» с кнопками «Редактировать»/«Удалить» → заполняет форму со всеми полями акции → после сохранения возвращается на `/`. Удаление — через страницу подтверждения.

**С5. Интеграция через API.** Внешняя система вызывает `/api/v1/shares/` (список/поиск/создание/изменение/удаление) без авторизации.

**С6. Администратор разворачивает систему.** Поднимает Postgres и Redis, выполняет `add_shares` (загрузка всех акций), запускает celery beat и worker — цены начинают обновляться каждые 10 секунд.

## 9. Бизнес-правила, проверки и ограничения

* `figi`, `ticker`, `uid` акции уникальны; `ticker` не длиннее 10 символов (`dashboard/models.py:7-12`).
* Обязательны `figi`, `isin`, `name`, `ticker`, `currency`; `uid` обязателен в HTML-форме (`dashboard/forms.py:11`), но **отсутствует** в API (`dashboard/api/v1/serializer.py:9-19`).
* Цена «растёт» (`is_trend_high = True`), если новая цена ≥ предыдущей; если предыдущей нет — тоже «растёт» (`dashboard/tasks.py:16-22`).
* В цену записывается только целая часть (`units`) котировки (`dashboard/services/market_data.py:11`), на графике — тоже (`graph.py:20`).
* Регистрация: email обязателен и корректен, пароли должны совпадать, email не должен быть уже зарегистрирован (`user/forms.py:30-46`). Иных требований к паролю нет.
* Вход: email приводится к нижнему регистру (`user/views.py:19`).
* Создавать/изменять/удалять акции через HTML могут только вошедшие пользователи; любые вошедшие, без разделения на роли.
* Список: сортировка по названию, 100 записей на страницу (HTML и API).

## 10. Функциональные требования

Нумерация сквозная; в скобках — где это реализовано.

**Справочник и просмотр**

* **ФТ-1.** Система хранит акции с атрибутами FIGI, ISIN, наименование, тикер, валюта, UID, текущая цена, признак роста цены, время последнего обновления (`dashboard/models.py:4-17`).
* **ФТ-2.** FIGI, тикер и UID акции уникальны в справочнике (`dashboard/models.py:7,10,12`; `migrations/0002`, `0003`).
* **ФТ-3.** Главная страница доступна без входа и показывает список акций с колонками «Тикер», «Название», «ISIN», «Текущая цена» (цена с кодом валюты) (`dashboard/views.py:20-26`; `templates/dashboard/list.html:16-40`).
* **ФТ-4.** Список отсортирован по наименованию и разбит на страницы по 100 акций с навигацией «назад/номера страниц/вперёд» (`dashboard/views.py:25-26`; `list.html:60-80`).
* **ФТ-5.** Ячейка текущей цены окрашивается зелёным, если признак роста установлен, и красным иначе (`list.html:35-40`).
* **ФТ-6.** Если акций нет, вместо таблицы выводится «Акций еще нет» (`list.html:83-85`).
* **ФТ-7.** Тикер в списке является ссылкой на карточку акции (`list.html:32`).
* **ФТ-8.** Карточка акции доступна без входа и показывает наименование, текущую цену с валютой и время последнего обновления (`dashboard/views.py:29-38`; `detail.html:11-13`).
* **ФТ-9.** Карточка акции содержит линейный график цен закрытия дневных свечей за последние 180 дней, получаемых из Tinkoff Invest API в момент открытия страницы (`dashboard/services/graph.py:11-36`; `detail.html:22-25`).

**Пользователи**

* **ФТ-10.** Гость может зарегистрироваться по email и паролю с подтверждением пароля (`user/forms.py:8-28`; `user/views.py:36-55`).
* **ФТ-11.** Регистрация отклоняется с сообщением «Введенные пароли не совпадают», если пароли различаются (`user/forms.py:35-37`).
* **ФТ-12.** Регистрация отклоняется с сообщением «Данный e-mail уже зарегистрирован!…», если пользователь с таким email уже есть (`user/forms.py:39-46`).
* **ФТ-13.** После успешной регистрации пользователь автоматически входит в систему и перенаправляется на главную (`user/forms.py:48-53`; `user/views.py:46-49`).
* **ФТ-14.** Пользователь входит по email и паролю; при неверных данных показывается «Неверный логин или пароль! Повторите попытку.», при успехе — переход на главную (`user/views.py:16-33`).
* **ФТ-15.** Вошедший пользователь видит в шапке приветствие с email и кнопку «Выход»; гость — кнопку «Войти» (`templates/dashboard/base.html:37-43`).
* **ФТ-16.** По кнопке «Выход» пользователь разлогинивается и перенаправляется на главную (`user/views.py:58-64`).

**Ведение справочника (HTML)**

* **ФТ-17.** Вошедший пользователь может добавить акцию через форму со всеми редактируемыми полями модели; после сохранения — переход на главную (`dashboard/views.py:41-46`; `forms.py:6-11`; `list.html:9-13`).

* **ФТ-19.** Вошедший пользователь может удалить любую акцию после подтверждения на отдельной странице (`dashboard/views.py:58-63`; `delete.html`).
* **ФТ-20.** Кнопки «Добавить», «Редактировать», «Удалить» показываются только вошедшим; при попытке гостя открыть страницы создания/изменения/удаления он перенаправляется на главную (`list.html:9,23,41`; `dashboard/views.py:11-17`).

**REST API**

* **ФТ-21.** API `/api/v1/shares/` поддерживает получение списка, получение одной акции, создание, полное и частичное изменение и удаление (`dashboard/api/v1/views.py:16-18`; `router.py:5-6`).
* **ФТ-22.** API возвращает поля `id, figi, isin, name, ticker, currency, last_price, is_trend_high, updated_at` (`dashboard/api/v1/serializer.py:9-19`).
* **ФТ-23.** Список API пагинируется параметрами `limit`/`offset`, по умолчанию 100 записей (`config/settings.py:31-35`).
* **ФТ-24.** Список API фильтруется по точному совпадению `name` и `ticker` (`views.py:10-13`), ищется параметром `search` по наименованию (регулярное выражение) (`views.py:22`), сортируется параметром `ordering` по `name` и `ticker` (`views.py:21`).
* **ФТ-25.** Обращение к несуществующей акции в API возвращает 404; невалидные данные — 400 (`dashboard/tests.py:54-56,78-89,105-109`).

**Интеграция с Tinkoff Invest API**

* **ФТ-26.** Команда `python manage.py add_shares` загружает из Tinkoff Invest API все доступные акции и добавляет отсутствующие в справочник (FIGI, наименование, ISIN, тикер, валюта, UID) (`add_shares.py:11-22`).
* **ФТ-27.** Система периодически (каждые 10 секунд по расписанию Celery beat) для каждой акции справочника запрашивает последнюю цену и сохраняет её как текущую (`config/celery.py:13-18`; `tasks.py:7-26`).
* **ФТ-28.** При обновлении цены признак роста устанавливается в «растёт», если новая цена не меньше предыдущей или предыдущей цены не было, иначе — в «падает» (`tasks.py:16-22`).

# Новая функциональность (задание 4)

## 19. Функциональные требования

Нумерация НФТ («новое функциональное требование»). Всё, кроме истории цен, доступно только вошедшему пользователю, и каждый видит только свои данные: чужие объекты отдают 404.

### 19.1. История рыночных цен

* **НФТ-1.** При каждом обновлении цен (задача Celery `update_last_price`) система сохраняет в БД запись «акция, цена, время», если цена изменилась по сравнению с последней сохранённой записью этой акции. Одинаковые цены подряд не дублируются.
* **НФТ-2.** Для каждой акции доступна страница истории `/history/<id>/`, открытая без входа, с выбором периода: 1 день, 7, 30, 90, 365 дней, «всё время» или произвольный интервал дат «с … по …».
* **НФТ-3.** Для выбранного периода система показывает цену на начало и на конец периода, абсолютное изменение, изменение в процентах, минимум, максимум и число записей. Цена на начало — последняя известная цена на момент начала периода, а если её нет — первая запись в периоде.
* **НФТ-4.** По накопленным данным строится график цены за период и выводится таблица записей, новые сверху.
* **НФТ-5.** Если записей за период нет, выводится сообщение об этом, расчёты не выполняются.
* **НФТ-6.** Команда `generate_demo_prices` заполняет историю синтетическими ценами (случайное блуждание с фиксированным зерном), но **только** для демо-акций с `uid`, начинающимся на `demo-`, чтобы выдуманные данные не смешивались с настоящими.

### 19.2. Персональный мониторинг акций

* **НФТ-7.** Пользователь создаёт, переименовывает и удаляет свои списки наблюдения.
* **НФТ-8.** В список добавляется акция из справочника; одна акция может быть в списке только один раз.
* **НФТ-9.** Для акции в списке задаётся один или несколько ценовых уровней: «цена ≥ X» (рост до уровня) или «цена ≤ X» (падение до уровня). Цена X положительна.
* **НФТ-10.** После каждого обновления цен система автоматически проверяет все активные уровни по новым ценам. При выполнении условия создаётся уведомление «акция, уровень, фактическая цена, время», а уровень помечается сработавшим.
* **НФТ-11.** Сработавший уровень больше не создаёт уведомлений, сколько бы обновлений цены ни прошло. Это гарантирует и уникальное ограничение в БД: «одно уведомление на одно срабатывание уровня», поэтому дублей нет даже при параллельной обработке.
* **НФТ-12.** Пользователь может снова включить сработавший уровень. Тогда следующее выполнение условия считается новым событием и создаёт новое уведомление.
* **НФТ-13.** В шапке сайта показывается число непрочитанных уведомлений; на странице уведомлений их можно отметить прочитанными.

### 19.3. Виртуальный инвестиционный портфель

* **НФТ-14.** Пользователь создаёт, переименовывает и удаляет свои портфели.
* **НФТ-15.** В портфеле моделируются операции «покупка» и «продажа»: акция, количество (целое > 0), цена (> 0; по умолчанию подставляется текущая цена акции), комментарий. Время операции — момент её создания.
* **НФТ-16.** Продать можно не больше, чем есть в портфеле на момент операции; иначе операция отклоняется с сообщением.
* **НФТ-17.** По каждой акции портфеля рассчитывается: количество, средняя цена приобретения (по методу средней стоимости: покупка пересчитывает среднюю, продажа её не меняет), вложено (средняя × количество), текущая цена и стоимость, нереализованная прибыль/убыток в рублях и процентах, реализованная прибыль/убыток от продаж.
* **НФТ-18.** По портфелю в целом — сумма вложений, текущая стоимость, нереализованная, реализованная и итоговая прибыль/убыток. Позиции без известной текущей цены показываются с пометкой «нет цены» и не входят в текущую стоимость.
* **НФТ-19.** Доступна история операций портфеля, новые сверху. Операции не редактируются (журнал неизменяемый); удаляется только портфель целиком.

### 19.4. Симулятор инвестиционных стратегий

* **НФТ-20.** Пользователь создаёт, изменяет, включает, выключает и удаляет стратегии. Стратегия — правило для одной акции: «купить N штук, если цена ≤ уровня покупки; продать всю позицию, если цена ≥ уровня продажи», плюс необязательный стоп-лосс «продать, если цена ≤ уровня стопа». Должно выполняться: стоп < уровень покупки < уровень продажи. Позиция одна: пока акция куплена, новые покупки не делаются. При заданном стоп-лоссе покупка возможна только при цене выше стопа (иначе позиция сразу закрылась бы по стопу).
* **НФТ-21.** После каждого обновления цен система автоматически применяет активные стратегии к новой цене и записывает виртуальные сделки в журнал стратегии: сторона, количество, цена, время, причина («цена ≤ уровня покупки», «цена ≥ уровня продажи», «стоп-лосс»).
* **НФТ-22.** Для стратегии рассчитываются показатели эффективности: число сделок, число закрытых циклов «покупка → продажа», доля прибыльных циклов, реализованная прибыль, нереализованная прибыль открытой позиции по текущей цене, итоговая прибыль и доходность в процентах на задействованный капитал (максимальная стоимость покупки).
* **НФТ-23.** Стратегию можно прогнать на накопленной истории цен за выбранный период (бэктест). Результат — список модельных сделок, те же показатели и сравнение с пассивной стратегией «купить в начале периода и держать». Бэктест в журнал не записывается.

## 20. Изменения архитектуры

* Новое Django-приложение **`investments`**: модели, формы, представления и шаблоны всех четырёх функций. Приложение `dashboard` (справочник и API) меняется минимально.
* **Сервисный слой** `investments/services/`: `history.py` (запись и статистика), `alerts.py` (проверка уровней), `portfolio.py` (расчёт позиций), `strategies.py` (движок стратегии). Сервисы — обычные функции, их можно тестировать без HTTP и без Celery.
* **Конвейер обработки цен:** задача `dashboard.tasks.update_last_price` после сохранения новых цен вызывает `investments.services.on_prices_updated()`. Она по очереди сохраняет историю, проверяет уровни и запускает стратегии, причём ошибка в одном шаге логируется и не останавливает остальные. Новых периодических задач и процессов не появилось.
* **Деньги** в новых моделях хранятся в `DecimalField` (а не `float`, как `Share.last_price`), чтобы суммы портфеля считались без ошибок округления.
* Шапка сайта: для вошедших — ссылки «Наблюдение», «Уведомления (N)», «Портфели», «Стратегии» (контекст-процессор `investments.context_processors.notifications`). Ссылка «История цен» — на карточке акции.

### Проверка

* **Автотесты:** 84 теста проходят — 41 прежний (регрессий нет) и 43 новых. Каждое НФТ покрыто тестом, номер требования указан в docstring.
  * Отсутствие дублей уведомлений (НФТ-11) проверено тремя способами: цена держится выше уровня 5 обновлений подряд → одно уведомление; одна и та же пачка цен обрабатывается дважды (повтор задачи) → одно уведомление; прямая вставка дубля → `IntegrityError` от ограничения БД.
  * Расчёты портфеля сверены с ручным расчётом: покупка 10 по 100 и 10 по 120 → средняя 110; продажа 5 по 140 → реализовано 150; остаток 15 по текущей цене 130 → стоимость 1950, нереализовано 300 (18,18 %).
  * Конвейер «задача Celery → история цен» проверен с моком SDK, как и в разделе 18.
* **Ручная проверка в браузере** на демо-данных (`loaddata demo_shares` + `generate_demo_prices`, демо-пользователь): история цен SBER за 90 дней (статистика и график), создание стратегии и бэктест «всё время», создание портфеля и покупка LKOH по текущей цене.
* **Ошибки, найденные при проверке и исправленные:**
  1. `Decimal("100").normalize()` в тексте уведомления печатался как `1E+2`. Нашёл тест, исправлено функцией `fmt()`.
  2. Стратегия после стоп-лосса сразу покупала снова, потому что цена была ниже и стопа, и уровня покупки, и на каждом обновлении цены продавала по стопу: 92 сделки в бэктесте вместо 4. Нашлось при ручном бэктесте, а не тестами: в тестах не было такого сценария. Правило уточнено (покупка только выше стопа, НФТ-20), добавлен регрессионный тест.

### Ограничения

* **Живые срабатывания** (уведомления и сделки стратегий по реальным ценам) в запущенном приложении не наблюдались: цены из T-Invest API не приходят (раздел 18). Логика проверена тестами с моками и бэктестом на демо-истории.
* **Демо-история** синтетическая (случайное блуждание): её доходности ничего не говорят о реальном рынке.
* **Уведомления** только внутри приложения (страница и счётчик), без email и Telegram: в требованиях способ доставки не задан.
* **Время** на страницах показывается в UTC, как в исходных настройках проекта (`TIME_ZONE = "UTC"`).
* **Комиссии брокера и налоги** в портфеле и стратегиях не учитываются; дробные лоты не поддерживаются (количество — целое).
